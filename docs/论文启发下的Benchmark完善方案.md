# 用论文方法完善当前 VISTA Benchmark

日期：2026-10-29（北京时间）。这是针对本机现有源码和真实运行的实施方案。第一阶段模块已经接入并完成单元测试和小规模真实验证；多种子、多任务的冻结实验仍未运行。现有结果和原生评估器保持原样。

## 1. 结论与文献依据

优先完成“可见状态账本 → 完成前核验 → 无进展恢复 → 成对重复实验”。第一阶段已实现状态账本、证据帧引用、公开动作回执、检查预算和恢复提示；下一步用冻结的多任务/多种子实验确认它是否稳定提分。先不铺开全部 28 篇论文、全部游戏和全部指标。

本次直接核对了以下一手资料：

- [VISTA 原文](https://arxiv.org/html/2610.02200v1)，重点为 §4.3、附录 A.2–A.4。其递进消融报告：连续对话、笔记、视觉记忆与检查、精确像素读取分别有不同贡献；在其指定模型和预算下，加入视觉记忆与检查的配置由 70.05 提升到 94.10，完整配置为 99.00。该数字不适用于本机 DeepSeek，也不能作为本机预期收益。原文还明确区分了增加预算与增加能力模块。
- [GameWorld 原文](https://arxiv.org/html/2604.07429v1)，重点为 §3.4–3.5、§4.5.2–4.5.3。核心是状态验证、暂停推理的协议，以及记忆长度和动作合法性分析。原文的记忆实验中，更长历史对不同接口的收益并不一致；因此不能把“多塞历史截图”当成必然提分的方法。
- [BrowserGym Ecosystem](https://arxiv.org/abs/2412.05467) 与[官方代码](https://github.com/ServiceNow/BrowserGym)。可借鉴统一生命周期、实验配置、跨任务管理和轨迹分析，不必为了采用这些原则重写现有运行时。

用户综述中的 Schema、Kepler、Explore Before You Solve 等其余资料，本次未逐篇核对全文、版本及实验数字。下文将“可执行假设、预测验证、捷径审计”等作为综述启发的设计建议，不将它们写成已复现的论文结论。历史检索记录保留在本地，未随本代码仓库发布。

第一阶段当前实现见 `src/vista/reliability.py` 和 `src/vista/backends/api.py`：`reliable`、`verified`、`ledger`、`legacy` 四个预设已接入 GameWorld、AI GameStore 和 ARC3 API 路径。状态卡和验证是 Agent 对公开证据的自评，`semantic_evidence_accuracy`、`state_accuracy`、`recovery_success_rate`、`strict_success` 仍保留为 `null`，没有独立标注时不冒充真实分数。

现有 `baseline` 与 `vista` 都使用连续对话、相同图像保留和相同注册工具，GameWorld 中也都包含上游 VISTA 方法提示。它们不是“无记忆 vs 有记忆”，只是额外提示不同。原有命名应继续保留以追溯旧结果，报告中明确叫作“基础提示/增强提示”。

本机 MC 泥土任务揭示了具体故障：

- 基础提示：17/20，100 次决策，51 次合法环境动作，49 次纯文字最终回复；多次声称已经采集完毕。
- 增强提示：20/20，50 次决策及动作，0 次纯文字最终回复。
- 不能把“100 次决策 vs 50 次决策”解释成环境动作减半，两个配置的实际动作是 51 vs 50。
- 该轨迹支持“误判完成及空转是应优先处理的问题”，尚不能从一次运行证明它是所有失败的主要原因。

## 3. 保留原生评分，新增诊断指标

建立两个明确标识的评测系列：

1. **原生任务评测**：冻结上游任务、目标、动作空间、重置、终止与计分规则。比较不同 Agent 模块；新增统计放在附加报告，不修改 `progress`、`success` 和官方分数。
2. **可靠性扩展评测**：增加过程约束、噪声、干扰、建筑任务等。使用新 suite/protocol ID 和独立结果表，分别报告原生目标成功和扩展严格成功。

如果新增语义动作、自动挖掘宏、DOM/背包 API 或额外状态提示，就改变了动作或观察协议，不能继续声称与纯视觉键鼠轨道完全可比。

首批指标限定为可可靠计算的项目：

| 指标 | 明确定义 | 边界 |
| --- | --- | --- |
| 目标成功率 SR | 冻结任务集合中环境确认成功的比例 | 同时报总尝试数、有效运行数和基础设施失败率；两种分母不可混用 |
| 原生进度 PG | 各任务 evaluator 的原始进度 | 保留上游最高进度与最终进度差别；不同 suite 不混合平均 |
| 扩展严格成功 | 原生目标成功且所有预先定义的硬约束通过 | 仅在扩展任务使用；无法验证时为 unknown，而非直接通过 |
| 合法执行率 | 被接受且执行的环境动作 / 环境动作尝试 | 不等于有用动作率；等待可以是正确动作 |
| 纯文字轮次率 | 无注册工具调用的回复轮数 / 决策轮数 | 区分正常最终提交与未终止时的反复提交 |
| 可见状态估计准确率 | Agent 对可观测字段的主张与同时间环境真值一致的比例 | 只在字段当时可辨认且有标注时计入；不可见/不确定单列 |
| 证据引用覆盖 | 关键状态主张中带有效 episode/frame/region 引用的比例 | 引用存在只表示可追溯，不证明证据支持，更不证明模型因果使用了它 |
| 证据支持率 | 抽样人工核验中，所引截图确实支持该主张的比例 | 冻结标注规则、双人标注和分歧处理；可自动核验的字段另报 |
| 恢复率 | 预定义干扰后，在 K 个决策内恢复到预定义正确状态的比例 | K、干扰时刻、对照组与恢复条件提前固定 |
| 成本与延迟 | 调用、图像视图、token、真实账单/估计费用、p50/p95 延迟、总时长 | thinking token 不重复加到已包含它的 completion token；无价格来源时不填费用 |

若检查虚假“已完成”声明，应单独标注明确的终止主张，并与当时的私有成功状态比对；自然语言规则提取需要人工抽检，不能再按关键词给任务加分。

不以任意权重计算新的“综合 100 分”。先在固定预算下比较 SR/PG，再展示成功率—token、成功率—时间曲线。成功运行的动作效率与失败运行的动作消耗分开报告，避免“提前失败所以动作少”被视作高效。没有人类或参考轨迹时，不报告虚构的人类相对效率。

## 4. P0：可见状态账本、核验和恢复

### 4.1 可见状态账本

沿用 WORKING.md，但增加简短、结构化的状态卡。每次只记录影响下一步动作的事实：

```json
{
  "episode_id": "...",
  "decision_id": 23,
  "beliefs": [
    {
      "field": "visible_hotbar.dirt",
      "estimate": 17,
      "status": "uncertain",
      "evidence": [{"frame_id": "...", "region": [0, 0, 1, 1]}]
    }
  ],
  "subgoal": "确认本轮泥土采集量，再选择下一处可挖方块",
  "expected_change": "挖掘后可见泥土计数增加",
  "next_verification": "对比挖掘前后快捷栏截图"
}
```

区域坐标这里只是格式占位；正式 schema 必须声明单位、原图/缩放坐标和转换关系。状态卡属于 Agent 的估计，不能混成 evaluator 真值。

对 MC 特别要分清初始库存、当前可见库存、累计采集与放置消耗。当前上游任务按 `item_gains.dirt` 判断新增采集，不能只用最终库存减初始库存推算，也不能假定某个快捷栏总数就是本轮收益。不确定时回看初始帧和关键变化帧。

### 4.2 核验器与权限

核验器分两种，独立配置：

- **Agent 可用核验器**：只读取该 Agent 已获得的截图、工具回执和它自己的状态卡，检查“预测与可见变化是否一致”，输出可解释的支持/矛盾/未知。
- **事后评测核验器**：可读取私有游戏状态，核对实际采集量、目标和违规。输出只进入报告，不在执行中反馈给 Agent。

不能因为某步没有增加隐藏进度，就把“没有进展，请换策略”从 evaluator 发给纯视觉 Agent。这会泄漏它原本不知道的状态。若研究 oracle/state-assisted 条件，独立开轨并公开其额外信息。

### 4.3 完成前检查与无进展恢复

- 公共任务仍在继续时，遇到“已完成”主张，要求检查该主张所依据的公开证据；若不确定，使用 inspect，或选择合法的下一步。停止信号仍由环境决定。
- 已有最终文字提交如果消耗一次原生决策，就继续照常计费计步。不要在后台免费重试、删掉这轮或把失败改成成功。
- 在可见状态卡未变化、相同动作反复执行等信号下触发恢复。可先以连续 3 轮作为开发集参数候选，正式测试前冻结；等待动画等合法重复需排除。
- 恢复采用固定有限序列：重新观察 → 回看相关帧 → 更换局部视角/位置 → 修改子目标。仍失败就明确记录原因或预算耗尽，不无限重置。
- 画面哈希不同不代表任务有进展，哈希相同也不必然表示失败。动画、相机变化、等待动作需结合公开语义状态判断。

首轮可验收标准是：每个核验和恢复事件有触发依据及预算记录；Agent 永远取不到私有库存/进度；在同预算未调参任务上报告收益或负面结果，而非只看原有 seed=42。

## 5. P1：把已有视觉工具做成可消融模块

“最近 8 张图片 + 全部文本”只是当前实现，不应成为固定最优设置。历史图像仍可完整归档，模型每次只接收与问题相关的少量视图。图像保留上限、文本压缩阈值、检索数与截图分辨率都要记录。

记忆消融至少分为：

1. 当前观测：只保留本决策观测及协议必要回执，不提供历史图片、history 和持久笔记。
2. 文本摘要：当前观测 + 有长度限制的摘要；关闭旧帧检索。
3. 视觉回看：当前观测 + 相同文本摘要，增加历史帧检索。

不能仅设 `image_history=1` 就称为无记忆；旧对话文字、笔记、history、inspect 仍可能泄漏全部历史。多帧 GameStore 的“当前观测”应保留同一决策的全部规定帧，不能被一张图的限制误删。

主动观察另作一个消融：固定频率/固定区域检查 vs Agent 自选帧与区域。固定相同的总观察预算或图像/token 上限，记录实际使用量；“只能看一次”和“每次返回 16 张图”不能算同样成本。

第一轮优先检查背包数字、目标方块、迷宫转角等关键区域。不把像素读取理解为自动语义识别；它提供数值，仍需 Agent 判断。保存的原图与模型接收到的变换图分开哈希。

## 6. P2：ARC 的可检验规则假设

当前 ARC 思考运行已通过 1/7 关，但非思考和思考配置同时改变了输出 token、调用和动作上限，不能据此证明只开启思考就有效。

先固定协议，再加入小型假设表：动作前预测对象位置/朝向/可达性变化，动作后用公开帧验证，保存支持、反例和未知。用下一次未见状态测试预测；只拟合已有轨迹不能证明世界模型能泛化。

可执行状态转移模型和规划器放到后续独立 scaffold。若增加代码执行，必须声明额外工具和计算预算，隔离游戏代码与私有状态；不要通过读取游戏源代码得到规则。VISTA 本身并不要求程序合成，不能把世界模型代码当成复现它的必要条件。

## 7. 分阶段实验，不直接启动巨型矩阵

### 开发试验：先定位收益

选 MC 的 2 个任务和 3 个开发种子；在重置确定性检查通过后，做 4 种逐步配置：

- A：冻结当前增强提示与工具。
- B：A + 状态卡。
- C：B + 可见证据核验。
- D：C + 有限恢复。

合计 `2 × 3 × 4 = 24` 次。此为递进工程诊断，只估计逐步加入模块的边际变化，不能独立估计所有交互效应。seed=42 的旧轨迹作为调试材料，不当作未调参测试集。

可沿用当前 MC 的 100 次原生决策、110 次模型调用、每次输出上限 2048 token、900 秒会话预算、固定关闭思考，所有配置相同。24 次会话预算合计上限为 6 小时，另有启动/清理开销；这不是费用估计。真正执行前先用少量运行测成本并限定总开支。

### 冻结测试：证明可重复

冻结最佳开发配置后，与 A 比较；使用 5 个采集任务 × 5 个未参与调参的种子 × 2 个配置，共 50 次。它评估的是同一浏览器游戏内的迁移和稳定性，不证明正式 Minecraft 或跨游戏泛化。开发过的任务与未开发过的任务分别报告。

先检查相同 seed 重置是否得到一致初始状态/帧/关键字段；相同 seed 不保证模型输出或浏览器时间过程完全确定。按 task/seed 配对并随机交错配置执行，减少服务时段和机器负载偏差。任务与 seed 清单、模型 ID、提示哈希、工具 schema、预算、失败策略在启动前保存。

报告成功数/总数、PG 均值、离散程度、失败分类、配对差值及 95% 区间。区间应按任务/种子的层次结构计算；任务很少时区间仅作探索性估计，不能用大量相关步骤伪装大量独立样本。API/浏览器故障单列，同时报告全部尝试与有效运行，不静默重跑后择优。

首次尝试分数须在配置冻结后，对每个测试局面只取第一次尝试，重复运行另报分布；失败后重试的成本不能藏起来。公开任务可能被模型训练或已有调试覆盖，新种子也不等于新规则。要研究外部泛化，另留未参与开发的游戏族或程序化生成的私有局面，并记录生成器和重置版本。

### 研究消融：验证模块来源

完成干净条件后，再做用户建议的 `2（当前观测/视觉回看）× 2（无核验/可见证据核验）× 3（干净/观测噪声/动态干扰）`。

例如 5 任务 × 5 种子 × 12 条件就是 300 次，另加重复次数才是总成本。先固定模型、动作粒度、摘要、恢复策略和思考配置。噪声只作用于 Agent 观测，不污染私有真值；延迟须声明游戏推理时是否暂停。当前 GameWorld 为暂停推理模式，实时游戏必须另立协议。

在线 ARC 的环境由远端服务生成，不能仅因配置写了同一个 seed 就称为可控的种子配对。以实际游戏版本、初始局面及官方服务允许的控制条件为准。

## 8. 有效性审计与完整 trace

增加不调用模型的随机合法动作、重复动作、盲动作、空提交控制器。它们只取得公开动作空间，不能读取评分或游戏代码。简单策略成功说明任务可能测不到预期能力；需要分析任务特性，不自动判定环境有漏洞。

MC 专项审计包含：初始泥土不计采集；放置后挖回、重复获得、重置后累计、达到目标再丢弃等情况。先记录上游原生行为；若设计“净采集”“禁止回收初始物资”等新目标，另建版本，不能偷偷改旧评分。

统一事件至少包括：`episode_id / event_id / parent_id / model_call_id / tool_call_id / environment_step_id / decision_id / frame_id / monotonic_timestamp / game_tick / event_type / visibility`。关键事件为 observe、belief、prediction、action_attempt、action_receipt、verification、recovery、termination。

模型主张与原图引用属于 public trace；私有真值、目标校验和状态快照属于 evaluator trace。全部日志可审计不等于全部日志都向 Agent 开放。缺失的旧事件字段应标为 unavailable，不能事后编造当时的预测或时间戳。

回放分级：当前已有的日志/画面回放可以直接保留；只有环境支持快照恢复且重放后状态哈希一致，才声明可执行的确定性重放。音画录像和 JSON 浏览器不等于游戏引擎重演。

| `src/vista/benchmarks/gameworld/session.py` | 审计动作与文字提交的原生计数 | 100 次决策保持原规则；不通过免费重试掩盖空转 |
| `src/vista/localbench.py` | 独立模块参数、实验清单、数据划分和成对重复运行 | 单变量可追溯；不覆盖输出；ARC 不宣称虚假配对 |
| `scripts/report_results.py` | 新诊断指标、失败分母、配对统计、成本曲线数据 | 新指标与原生分数并列，缺失信息不当作 0 |
| `scripts/serve_benchmark.py` / `dashboard/index.html` | 展示证据支持、文字空转、核验与恢复、协议和预算差异 | 同类配置才能直接比较；不暴露私有记录接口 |

建议只为关键边界新增测试：私有状态不泄漏、无记忆条件确实无法取得历史、核验不能写成功、重置不继承旧 episode、原生决策计数不变、证据引用不能指向未来或别的运行。Agent 能否提分仍以真实环境实验为准，单元测试不算任务成绩。

## 10. 对接原工作目标

- **MC 建筑 Demo**：单独建立小尺寸目标结构与参考状态；先验证一个固定地基/墙体/门洞。报告方块类别与位置匹配、额外方块惩罚、连通/入口可达和完成步骤。规范允许的平移/旋转后才做结构对齐，避免错位置也算成功。由世界状态评分，模型对自己步骤的描述不能得分。
- **think/action 拆解**：记录观测可用到模型请求、模型返回、动作开始/结束、新观测到达。API 隐藏推理的内部耗时不可直接测量；只能报告模型请求端到端耗时、服务返回 token 和工具执行耗时。
- **饥荒/泰拉瑞亚**：后续接真实客户端/服务端 adapter；物品与 Boss 事件由私有状态检查，图像与键鼠按公开协议给 Agent。现有浏览器克隆的得分不能移作这些游戏的成绩。
- **Roguelite 关卡**：若是复刻一个可玩环境，先验收可达、触发与通关；若让 Agent 复建地图，另设布局/结构/可玩性评分，两个任务不能混为一个成功率。

首个可交付版本应是：冻结原生评分 + 3 个 Agent 改进模块 + 可追溯诊断报告 + 24 次开发实验的完整包。若模块没有提升或成本过高，保留负面结果，再决定是否进入 50 次冻结测试和 300 次研究消融。

## 11. 已接入本地实现

本目录的本地 VISTA fork 已把上述方案落到可复现实验基础设施：

- `task-protocol-v2` 为新运行保存公开任务规范、数据版本、种子、预算、计时模式和哈希身份；旧 v1 运行仍可读取；
- `reliable / verified / ledger / legacy` 保留原生 evaluator 分数，同时记录证据引用、状态卡、动作回执、检查和恢复事件；
- `run_matrix.py` 支持任务 × 种子 × 配置的冻结计划、逐任务状态写入和中断续跑；重试使用独立 attempt 目录，保留中断轨迹；默认只生成计划，避免未经安排的模型消耗；
- `building.py` 提供主机侧建筑状态评分，区分匹配、缺失、多余、材料错误和硬约束违规；
- `audit_gameworld.py` 当前只做 catalog/control-plan 审计，真正盲动作和重复动作控制仍需针对每个游戏 adapter 实现；
- `run_controls.py` 已在 MC 风格 `18_01`、seed=42 执行 text-only、repeat 和 blind 三个零模型控制器，均完整跑满 100 步并获得原生 0% 进度；
- `metrics.py` 将模型请求、游戏动作延迟、token、重试和传输错误纳入报告；动作日志按 tool-call ID 去重，避免把 inspect/状态卡调用计成游戏动作；缺少 usage 或独立语义真值时保留缺失值。
- `report_results.py` 对相同游戏/任务/种子做配对比较，任务内聚合后执行两级 bootstrap； dashboard 展示单次成本、非法动作率、矩阵条件汇总和配对差值。
- `clock_mode` 写入任务协议；当前 adapter 只接受 `paused`，实时 `wall/token` 模式在环境真正推进之前会拒绝运行。
- 离线回归测试覆盖 API 动作追踪、成本去重、矩阵续跑、建筑评分器、控制策略与任务协议。

这些新增字段是过程诊断，不替换 GameWorld、GameStore 或 ARC3 的原生分数。没有独立标注时，证据语义准确率、状态准确率和严格成功率保持 `null`。正式 Minecraft、饥荒和泰拉瑞亚尚未部署，不能把浏览器复刻结果写成正式游戏成绩。
