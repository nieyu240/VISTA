# 团队使用手册

## 环境与模型

Windows 使用 WSL Ubuntu 24.04；Linux 使用 Ubuntu 24.04 和 Python 3.12。先按根目录 README 安装。模型服务需要同时支持图像输入和原生工具调用，纯文本服务不能完成视觉游戏评测。

Linux 首次安装：

```bash
sudo apt-get update
sudo apt-get install -y git python3.12-venv
VISTA_SKIP_BROWSER_CHECK=1 bash scripts/deploy_local.sh
sudo "$HOME/.venvs/vista-benchmark/bin/python" -m playwright install-deps chromium
"$HOME/.venvs/vista-benchmark/bin/python" -m vista doctor
cp .env.example .env
# 用编辑器填写 .env 的 VISTA_API_KEY、VISTA_API_BASE、VISTA_MODEL
```

默认虚拟环境为 `~/.venvs/vista-benchmark`，数据为 `~/.local/share/vista-benchmark`。需要变更路径时，在 WSL / Linux 中配置 `VISTA_BENCH_VENV` / `VISTA_BENCH_DATA`；Windows 包装脚本可用 `-PythonPath` 指定 Linux Python 路径。

以下 Bash 示例都在 WSL / Linux 的项目根目录执行，先设置：

```bash
PYTHON="$HOME/.venvs/vista-benchmark/bin/python"
```

## 1. 单次评测

```bash
"$PYTHON" -m vista doctor
"$PYTHON" -m vista list --profile gameworld
"$PYTHON" -m vista run --profile gameworld \
  --game 01_2048 --task 01_01 --seed 42 \
  --env-file .env --output runs/2048-model-a-seed42
```

`--model` 优先于 `.env` 的 `VISTA_MODEL`。每次选择新输出目录；同一环境种子不保证模型输出确定。API 环境变量优先于 `.env`，切换服务时检查终端中已有的变量。

GameWorld 使用原生 100 次决策协议。`--max-calls` 限制模型调用；`--max-tokens` 是单次输出上限；`--task-timeout` 是会话时间预算。具体参数见 [API 参考](local-api.md)。

其他套件：

```bash
# AI GameStore：先列出游戏，再使用列表中的编号
"$PYTHON" -m vista list --profile aigamestore
"$PYTHON" -m vista run --profile aigamestore --game 1 \
  --env-file .env --output runs/gamestore-model-a-seed42

# ARC3：另外填写 .env 中的 ARC_API_KEY；需要官方在线服务
"$PYTHON" -m vista list --profile arc3 --env-file .env
# 将 GAME_ID 替换为上一条命令返回的真实游戏 ID
"$PYTHON" -m vista run --profile arc3 --game GAME_ID \
  --env-file .env --output runs/arc3-model-a
```

## 2. 基础提示与增强提示对比

```powershell
.\scripts\benchmark.ps1 -Command compare -Profile gameworld `
  -Game 01_2048 -Task 01_01 -ModelEnvFile .env -Output .\runs\2048-prompt-comparison
```

该命令连续执行两次真实评测，分别保存 `baseline` 与 `vista`。它只比较额外提示词，两组都保留注册工具。一次配对不能代替多任务、多种子实验。

## 3. 批量任务与模块对比

复制 `configs/mc-development-matrix.json`，按需修改：

| 字段 | 含义 |
| --- | --- |
| `model` | 可选；固定模型 ID，缺省使用 `.env` 的 `VISTA_MODEL` |
| `profile` | `gameworld` / `aigamestore` / `arc3` |
| `tasks` | 游戏与任务列表，来源于 `list` |
| `seeds` | 环境种子列表；ARC3 的在线生成不保证种子匹配 |
| `conditions` | 配置名称、提示策略、记忆、核验与恢复设置 |
| `max_calls` / `max_tokens` / `task_timeout` | 所有条件共享的调用、单次输出和时间预算 |

先生成计划；不调用模型：

```bash
"$PYTHON" scripts/run_matrix.py \
  --matrix configs/mc-development-matrix.json --output runs/mc-matrix
```

核对 `runs/mc-matrix/matrix.json` 后执行。示例为 18 次完整评测，使用模型服务额度：

```bash
"$PYTHON" scripts/run_matrix.py \
  --matrix configs/mc-development-matrix.json --output runs/mc-matrix \
  --env-file .env --execute
```

中断后执行同一条命令即可续跑；已产生结果的任务保留，未完成尝试写入独立目录。更换模型、配置或任务时使用新输出目录。Windows 用户可打开 WSL 终端运行以上命令。

### ARC 公开集总分

先获取官方目录并冻结游戏版本，再生成计划：

```bash
"$PYTHON" -m vista list --profile arc3 --env-file .env --output reports/arc-catalog
"$PYTHON" scripts/run_arc_suite.py \
  --catalog reports/arc-catalog/catalog.json --output runs/arc-public
```

核对计划后，用同样参数加 `--env-file .env --execute` 执行。默认每游戏 100 次动作、150 次逻辑模型调用、每次输出 2048 token、20 分钟会话预算，3 个游戏并发；25 个游戏最多 3,750 次逻辑调用。网络重试另记，最多 3 次 HTTP 尝试 / 逻辑调用。这是预算受限评测，与原上游默认 2,000 次动作不同。

`runs/arc-public/summary.json` 保留每游戏结果；全部游戏取得有效的已关闭官方分卡后才计算 `total_score`。总分为各游戏官方分数等权平均，沿用 ARC SDK 的游戏权重；未把多张分卡伪称为一张官方批次分卡。缺失和基础设施失败不会被剔除后计算总分。

余额不足、无效密钥或模型权限错误会阻止继续启动新任务。恢复服务后，用相同参数加 `--retry-infrastructure --execute`，只重试没有有效评分的基础设施失败，旧记录保留在原目录，新尝试写入 `attempts/`。有效的 0 分不会重跑；新增尝试会增加调用量，`model_calls_all_attempts` 记录全部尝试的逻辑调用数。`prompt_tokens` / `completion_tokens` 汇总当前所选尝试的已返回用量，完整费用应核对历史调用日志与服务商账单。

续跑保持初次记录的 Agent 源码提交；只修改文档或套件运行脚本后可以继续，Agent 源码、依赖配置、游戏目录或预算变化会被拒绝，需要建立新套件。2026-11-01 的预算受限重测及未完成原因见[结果报告](results/arc-public-20261101.md)。

## 4. 报告与回放

```powershell
.\scripts\benchmark.ps1 -Command report
.\scripts\open_benchmark.ps1
```

Linux 对应：

```bash
"$PYTHON" scripts/report_results.py
"$PYTHON" scripts/serve_benchmark.py
```

浏览器打开 `http://localhost:8765`。若端口已被占用，可使用 `open_benchmark.ps1 -Port 8766` 或 `serve_benchmark.py --port 8766`。

| 产物 | 用途 |
| --- | --- |
| `runs/<运行>/result.json` | 原生结果、错误与结束原因 |
| `runs/<运行>/task_protocol.json` | 任务、种子、预算、版本和计时协议 |
| `runs/<运行>/replay.html` | 保存画面与事件的回放，可直接用浏览器打开 |
| `reports/deployment/results.json` | 仪表盘使用的汇总数据 |
| `reports/deployment/部署与评测报告.md` | 可阅读的结果报告和配对统计 |

只有 `scored=true` 表示获得有效评分，仍需查看 `success` / `progress` 判断是否完成。动作数、模型调用、token 与耗时分开报告。不同模型要使用相同任务、种子和预算；不同套件的分数不直接混合平均。

`runs/` 可能含提示、截图和服务商响应，默认不进 Git。团队分享时先审查具体产物；分享源码不需要上传整份运行目录。

## 5. 有效性审计与建筑评分

```bash
  --game 18_minecraft-clone-glm --task 18_01 --seed 42 \
  --output runs/mc-controls-seed42

```

```bash
"$PYTHON" scripts/score_building.py \
  --target configs/building-demo-v1.json \
  --actual configs/building-demo-actual-perfect.json \
  --output reports/deployment/building-demo-fixture-score.json
```

实际建造验收需要游戏 adapter 导出方块坐标、材料和约束测量，再替换 `--actual`。示例满分只验证评分器。

## 6. 接入团队自己的游戏

保留统一评测产物，按以下顺序实现 adapter：

1. 定义可重置的初始状态、任务目标、种子、允许动作、预算和失败条件。
2. 向 Agent 提供截图与公开工具；将真实环境状态和成功检查器保留在主机侧。
3. 执行动作后记录观察、动作回执和状态转移；由检查器返回进度与成功状态。
4. 生成 `TaskSpec`（`src/vista/task_protocol.py`），保存版本和任务身份。
5. 沿用 `result.json`、调用 ID、`events.jsonl` 和回放，再加入矩阵与控制实验。

参考 `src/vista/benchmarks/gameworld/` 的 engine / session / evaluator 对接。纯视觉键鼠与结构化状态工具应使用不同协议标识。新增指标需要可验证真值，不能用 Agent 自述代替环境计分。

## 常见问题

- **Chromium 缺库**：在 Ubuntu 安装 Playwright 系统依赖后重试；Windows 运行 `scripts/deploy.ps1`。
- **网络 / 代理**：在 WSL 设置 `VISTA_AUDIT_PROXY` 为可从 WSL 访问的代理地址，或使用现有网络环境。
- **无模型权限 / 不支持工具**：核对 `.env` 的服务地址、模型 ID 和图像 / 工具能力。`doctor -ProbeModel` 会发起一次付费检查。
- **结果页为空**：先完成一次评测；已有运行后执行 `report`。确保打开的是当前项目的查看服务。
- **脚本执行策略阻止运行**：在 PowerShell 使用 `powershell -ExecutionPolicy Bypass -File .\scripts\deploy.ps1`；该参数只作用于这次进程。
