# Minecraft 饥荒 泰拉瑞亚与关卡复刻的 benchmark 接入方案

目标是把 VISTA 的视觉观察、记忆和工具调度接到真实游戏，取得可验证、可复现的任务成绩。当前已确认基础 WSL 环境可用，但游戏适配器、可重置任务环境和自定义评估器尚未实现。

## 目标选择与本机约束

| 目标 | 建议的首批任务 | 私有评估证据 | 部署前需确定 |
| --- | --- | --- | --- |
| Minecraft | 定点导航、固定配方制作、有限区域方块搭建 | 服务端坐标、物品事件、方块差异、死亡事件 | Java／基岩／教育版，版本，存档，模组或桥接方式 |
| 饥荒 | 固定世界中的采集、制作、生存与抵达目标 | 游戏内物品、时间、生命与任务事件 | 单机／联机版、版本、Lua／服务端评估能力 |
| 泰拉瑞亚 | 导航、采集、制作、受控战斗、区域搭建 | 游戏状态、背包与地图变化 | 版本、是否使用 tModLoader、存档与评估插件 |
| 关卡复刻 | 复建小型可玩关卡，或按参考图搭建 | 地图快照、目标结构、可达性、通关触发器 | 参考材料、交互规则、评分容差、属于哪一种复刻任务 |

Minecraft Java 版是便于受控模组桥接的候选基线，已有教育版不能视为 Java 环境已经安装。可考虑固定 Minecraft Java 1.21.1 与 Java 21 作为一个开发组合；这只是方案选项，实际部署仍应由选定客户端和模组兼容性决定。不要直接把旧版 Malmo／MineRL 的运行约束套到当前 VISTA Python 3.12 环境。

资源有限的电脑首轮建议一个客户端、一个任务，先测量 720p 左右画面的实际采集延迟与游戏帧率。模型推理走远端；不把本机大模型部署作为前置条件。

## 运行边界

```text
Windows 游戏客户端与本地测试世界
        │ 真实画面、受控键鼠或游戏内动作
Windows 游戏桥接进程
        │ 明确的任务、动作、帧编号和请求编号
WSL VISTA TaskSession → TaskRuntime → Codex 或未来的视觉模型 backend
        │ 独立保存的私有状态和事件
主机侧 evaluator → result 与评测证据
```

Windows 和 WSL 之间的桥接还没有部署。需先验证互通地址与监听范围；游戏桥只接受约定的动作及任务操作，不接受任意 shell 命令。模型只取得任务描述、允许的工具与画面，评估器的目标状态、隐藏坐标和答案不放入模型可见目录。

代码入口可以复用现有 `vista.core.contracts.TaskSession`、`PublicTask`、`Visual`、`ToolBinding` 和 `vista.core.runtime.TaskRuntime`。一个新游戏需要实现 session 与游戏桥，不需要复制整个 Codex runner。现有 `vista.cli` 的 profile 是固定列表，正式集成时需要增加新 profile 和包元数据；目前没有自动插件发现机制。

## 最小闭环

先做一个可确定判分的小任务，例如固定 Minecraft 测试地图中抵达指定区域。公开给模型的是任务说明和初始画面，判分依赖独立任务触发器。

1. `reset(task_id, seed, snapshot)` 恢复任务专用存档，清理输入状态，返回 `episode_id` 和初始帧。
2. `observe()` 截取真实客户端画面，记录 `frame_id`、内容哈希、尺寸和游戏时间。
3. `step(action, duration)` 应用允许的动作，等待协议规定的 ticks 或时间，返回新画面及动作执行回执。
4. evaluator 读取私有状态判定成功、失败或继续，不采信模型自报通关。
5. `close()` 释放按键、关闭任务资源，保存轨迹和最终状态。崩溃、中断、预算耗尽分别记录。

每个改变游戏状态的请求需要唯一 `request_id` 和去重规则，避免超时后重试导致双重点击或重复放置。连续持键应有最大持续时间和自动释放；重置应使用任务专用世界快照。

对于实时游戏，要声明模型思考期间世界是否继续推进。可控的 Minecraft tick 模式、饥荒时间机制和泰拉瑞亚单机／联机行为不能混为一个默认规则。协议必须记录这种差异，否则模型延迟会改变任务难度。

## 动作和信息协议

建议复用 VISTA 的 `play` 工具名，由游戏 session 定义具体动作 schema。Minecraft 可包含移动、转视角、攻击、使用、快捷栏与库存操作；2D 游戏可包含移动、跳跃、攻击、交互和库存操作。必须区分按下、释放、持续时间和同时输入，不能只让模型输出自然语言再按关键字计分。

坐标体系要明确是画面像素、窗口客户区坐标还是游戏内相对视角。截图尺寸、缩放、光标位置、窗口焦点及 HUD 设置应固定并写入 manifest。

`inspect`、`read_pixels`、`history` 和笔记能力可沿用 VISTA；是否开放以及预算大小应作为实验变量。若声称纯视觉评测，不把 DOM、游戏内坐标、背包状态或实体列表作为额外观察传给 agent。评估器可以读取这些状态，但只在主机侧使用。

## 关卡复刻的两种任务

**复建可玩的关卡环境**：先把参考设计实现为固定版本地图，验证入口、出口、机关与规则，再让 agent 在该地图中通关。评分围绕任务完成、动作效率和失败类型。

**让 agent 根据参考搭建关卡**：参考图、布局说明和允许材料是公开输入；目标方块／地块及结构约束由评估器保存。评分可同时报告区域对齐后的方块精确率、召回率、结构连通性和可玩性。仅有外观相似不能证明关卡功能正确。

这两类任务应分成不同 suite，不把“地图搭建完成”与“模型成功通关”合并计算。

## 结果和版本要求

每个任务应记录：游戏及模组版本、地图／存档哈希、种子、初始状态、操作协议版本、任务与评估器版本、VISTA commit 与源码指纹、模型身份、backend、提示与工具配置、预算。

每次运行应保存真实帧、动作与执行回执、环境时间、模型请求时间、评估证据和结束原因。主要指标包括任务成功率、有效动作数、reset 数、延迟、token 用量与可核实的成本。没有用量或价格来源时保留缺失值，不根据预算倒推成本。

成功率的分母必须说明是否包含基础设施失败。建议同时报告全部任务的结果分布，以及排除基础设施异常后的模型任务结果。状态至少区分：

- `success`：评估器确认达到目标。
- `task_failure`：死亡、破坏约束或明确任务失败。
- `budget_exhausted`：动作或时间预算耗尽。
- `infrastructure_error`：桥接、客户端、模型服务或采集故障。
- `incomplete`：运行中断或证据缺失。

跨游戏保留各自原生任务指标；在建立人类基线和统一协议之前，不把新的成功率称为 ARC 的 RHAE。

## 建议实施阶段

1. **部署与证据**：选定一个真实游戏版本和任务快照；打通游戏桥、截图、动作和 reset。修复 WSL 与模型容器的代理配置。
2. **无模型闭环**：固定脚本完成一个已知可成功的任务，确认随机／无效动作不会被误判成功，并验证状态恢复和轨迹重放。
3. **模型闭环**：复用干净 VISTA 的 Codex backend，小预算单任务运行；确认真实帧、真实动作和独立成功判定均完整。
4. **扩展任务**：加入导航、采集、制作、搭建或通关任务，固定种子并重复运行，记录失败分布。
5. **跨游戏复用**：为饥荒或泰拉瑞亚新增 adapter；其版本和控制协议单独固定。之后再增加模型和记忆能力消融。

现有 DeepSeek adapter 不可直接用于上述阶段：它需要用真实观察替换固定图片，实现结构化工具调用循环，并使用独立 evaluator。模型回复出现 `play` 或 `submit` 不能构成任务成功证据。
